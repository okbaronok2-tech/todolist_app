## 1. 개요

### 1.1 목적

구현자와 검증자가 그대로 따라 할 수 있는 사용자 관점 흐름을 정의한다. 각 시나리오는 수동 검증 체크리스트(PRD 9.1)의 입력으로 쓴다.

### 1.2 범위

- P0 기능 전체(F-01, F-02, F-04~F-11)를 다룬다.
- P1 기능 F-03은 US-19에만 두고 제목에 "(P1)"을 붙인다.
- 비범위는 도메인 정의서 1.4와 PRD 2.2를 따른다.

### 1.3 읽는 법

- 모든 시나리오는 3장의 초기 데이터에서 시작한다. 사전 상태에 따로 적은 내용만 다르다.
- 단계는 "사용자 행동 → 시스템 반응" 형식이다. `[ ]`는 버튼·링크, 괄호 안 경로는 화면 경로다.
- 오류 코드 뒤 괄호는 HTTP status다 (PRD 6.3). 거부 응답 본문은 `{ "code", "message" }`다.
- 화면은 데스크톱 1280px 기준이다. US-18만 375px다.
- "API 직접 호출" 단계는 화면으로 재현할 수 없는 서버 규칙 확인용이다. 브라우저 개발자 도구나 API 호출 스크립트(PRD R-05)로 수행한다.
- 날짜에서 연도를 생략하면 2026년이다. "할일 N"은 3.4 표의 id N인 할일이다.

## 3. 공통 전제

### 3.1 기준일과 환경

- 기준일 today = 2026-11-03(화)이다. 도메인 정의서 4.3 검증 예와 같다.
- today는 클라이언트 로컬 날짜다 (D-05). 검증 기기의 날짜를 2026-11-03으로 맞춘다.
- 캘린더 anchorDate 기본값은 오늘(11-03)이다 (PRD 4.2 가정).
- 샘플 데이터는 시드 SQL로 넣는다. id는 시드 순서대로 부여되고 `createdAt`도 id 순이라고 가정한다. 실제 id가 다르면 표의 id를 실제 값으로 바꿔 읽는다.
- 인증 쿠키는 `token`(액세스, 15분)과 `refresh_token`(리프레시, 14일) 둘이다 (PRD NFR-06). 토큰 만료는 브라우저 개발자 도구에서 해당 쿠키를 삭제해 대신 재현한다.

| 항목 | 내용 |

4. [카테고리 관리] → `/categories`(SC-07)에 '기본' 1개만 표시.

기대 결과:

- SC-01을 거치지 않고 SC-03에 진입한다 (UC-01 자동 로그인).
- `name = '기본'`, `isDefault = true` 카테고리가 정확히 1개다 (BR-11).
